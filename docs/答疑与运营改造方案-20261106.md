# 答疑、工作通知与 OSS 改造方案（2026-11-06）

## 本轮边界

本目录是独立交互原型，入口 http://127.0.0.1:18896 ，全为示例数据、没有 API 或费用。正式布局等待确认。密码显示、新建对话、错误说明是独立局部修复，另行验证发布。不得用本原型的示例状态当成正式业务已实现。

## 设计基准

沿用已确认的浅色和蓝色操作风格。桌面答疑侧栏 250px，正文最大 800px、输入区最大 850px；正文 15px/1.9，顶部标题 16px，辅助信息 12px。用户消息用浅灰短气泡，代码为浅色独立横向滚动区域，复制操作在代码栏。项目及知识放右侧按需展开面板，不挤占正文。输入区位于页面底部，正文独立滚动。

管理员消息为工作通知：390px 列表加详情区域，顶部按全部、待处理、业务更新、系统异常切换；不把通知全文全部拉长铺在列表。手机只展示列表或详情之一，保留返回入口。已读与业务已处理是两个状态。

帖子审核用最大 540px 弹窗，正文可以滚动，底栏始终可达，原因选填。审核动作遵循现有 APPROVE/HIDE/LOCK 等契约，不伪造“退回”后端状态。空原因仍保留操作人、时间、动作、对象及状态审计。

OSS 配置采用连接配置与迁移步骤两块区域。配置保存、权限检查、迁移校验、切换相互独立。凭证只写入不回显；本原型不要输入真实凭证。

已模拟：新建空对话、历史搜索、代码复制、引用原文、资料面板、示例发送、答疑加载/失败重试、通知筛选/详情、审核取消/空原因确认、OSS 必填检查和迁移门槛。未模拟完整分页、上传进度、多任务并发、真实权限与服务器故障；非答疑页面状态选择仅显示示意提示。

## OSS 实施方案

现状：现有 ObjectStorage 端口和 S3ObjectStorage 实际使用 MinIO/S3 配置；管理员存储记录是元数据与 credentialRef，不等于已经动态对接阿里云。不能只修改 endpoint 就宣称 OSS 接入完成。

1. 增加 OSS 适配器，使用锁定版本的官方 SDK；保留原 ObjectStorage 接口和扫描隔离流程。资产记录绑定具体 storageConfigId/版本，旧资产继续走原提供者，禁止全局切换造成旧文件不可读。
2. 管理员专属设置：区域、Bucket、RAM AccessKey ID/Secret、加密模式；端点由区域白名单生成，限制任意 URL、防 SSRF。服务端使用服务器独立主密钥进行 AES-GCM 加密，数据库只存密文和密钥版本；返回尾号/是否配置，日志、审计、备份报告不出现明文。保存、测试、切换权限独立，CAS 防覆盖，worker 使用版本化快照。
3. 私有 Bucket，禁用公共 ACL，HTTPS；SSE-OSS/AES-256 为默认方案，SSE-KMS 可选并提示额外配置和费用。服务器先校验用户及资产业务权限，再签发短时、限定对象和方法的访问地址；上传到隔离前缀，文件扫描通过才进入 READY。保持大小、摘要、类型和引用校验。
4. 封面增加尺寸合适的缩略图和懒加载，避免下载原图。短期签名在有效期内复用，防止每次渲染重复请求；需撤权立即生效的敏感文件走鉴权代理或更短 TTL。私有 CDN 回源和 CDN URL 鉴权是后续可选项，不自动购买或开通。现阶段未取得文件实际时延分解，不能承诺 OSS 能消除所有网络延迟。
5. 迁移清单记录旧/新对象、版本、大小、SHA-256、引用数量及失败原因。先复制后逐个验证，不删除旧对象。历史数据库里原本就缺失的文件单列，不能当作迁移成功。验证私有下载、封面、扫描、交付版本快照、Office/视频读取、失败重试与回滚。
6. 校验通过后切新上传，逐步切旧文件读取；全部引用脱离 MinIO 且回滚副本可用后才停 MinIO。ClamAV、Tika、Office 等不属于被替代的对象存储，继续保留。停服务不删除卷，不自动释放云资源。

保护边界：私有权限防止未授权读取，加密防止静态介质泄漏；签名 URL 是有效期内的持有者凭证。合法接收者仍可保存文件，不承诺“绝对无法盗取”。Referer 防盗链只能辅助，不能代替用户权限。

## 知识引用：采用 RAG，复用现有 PostgreSQL/pgvector

RAG 是检索增强生成的流程，向量库是其中一种检索基础设施，不是二选一。当前已有知识分片、索引代次、权限查询、SemanticSearchService/CompatibleEmbeddingGateway、pgvector knowledge_vector、embedding 审计和回答来源快照。RunService 已接受最多 8 个 sourceVersionIds，校验权限后将知识片段放入模型上下文，并保存引用。现有 UI 主要通过链接携带一个知识版本，尚不是每次提问自动按问题检索。

推荐分两步落地：
- 第一阶段：输入区可选择多条知识，自动进行有权限的已发布内容关键词检索，按相关性选择片段而不是把整份资料塞入上下文。先复用已有索引，不新增外部向量服务，不自动产生 embedding 费用。
- 第二阶段：配置可用 embedding 供应商后增加向量与关键词混合召回，以 RRF 等方式融合，评测后决定是否需要 rerank。复用 PostgreSQL/pgvector，当前 2核2GB 的测试服务器不额外部署独立向量数据库；大规模容量需单独压测。显式语义检索不可用时明确提示；自动检索模式可按设计允许可见的关键词降级，不能静默伪装语义检索成功。

建议流程：提问 → 解析项目/手动资料范围 → 服务端权限过滤 → 关键词/向量候选 → 去重排序、阈值、上下文 token 预算 → 再次验证版本与权限 → 冻结来源快照 → 生成 → 校验引用编号 → 保存回答、来源与实际用量。资料只作不可信数据，保留现有提示注入隔离。

引用必须显示标题、版本、段落/页码（没有真实页码则不编造）、原文片段。点击时再次授权。没有检索命中要明确说没有找到资料；模型输出不存在的编号不得渲染为有效引用；不得把“提供给模型的全部片段”误称为“回答实际引用”。文档下架、索引代次变更与权限撤销都有回归用例。查询 embedding、模型生成和重排分别记录成本，重复 SSE 不重复计费。

评测：用实际项目问题构建带期望引用的题集，测检索 Recall@k、引用支持率、无命中拒答、跨学生泄露、索引更新可见性、延迟和成本；先通过隔离测试再接真实付费供应商。

## 管理员工作通知

现有 NotificationMapper 以 recipient_id 限制收件人，不能仅因页面相似就断言读取了学生收件箱。需要在事件源增加面向管理员的工作通知，而非复制学生通知或修改历史学生消息。

|事件|管理员接收范围|目标|
|---|---|---|
|学生提交/补充需求|有项目处理权限的负责人，未分配时授权管理角色|需求详情|
|学生验收确认/反馈|项目负责人及授权管理角色|交付或验收记录|
|帖子进入待审/举报提交|有对应审核权限的管理员|帖子审核弹窗/举报详情|
|任务需要人工处理|有运维或账务权限的管理员|任务及核对详情|

同一事务写 outbox，冻结收件人快照，Rabbit/inbox 去重，重投不重复通知。业务类型、目标资源、事件版本与待处理状态为结构化字段，列表支持服务端分页筛选。已读仅改变收件箱状态，业务处理仍用对应接口及 ETag；目标权限收紧时显示不可访问，不泄漏原摘要。公告发布保留独立入口；学生私聊正文不进入管理员通知。
